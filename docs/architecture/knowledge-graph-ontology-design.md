# Knowledge-graph ontology design — methodology + ECommerceApp worked example

Source of truth for **how** we design a code-derived structural knowledge graph
(Neo4j nodes/edges generated by static analysis, not by an LLM reading source at
generation time) for this codebase, and **why** the ECommerceApp ontology looks the
way it does. Written up from the design session that produced
`tools/kg/seed/ontology.json` / `ontology.cypher`.

Two thin wrapper skills point here instead of duplicating this content:
- Claude Code: `.claude/skills/kg-ontology-designer/SKILL.md`
- GitHub Copilot: `.github/skills/kg-ontology-designer/SKILL.md`

Only the methodology and guardrails below are shared between the two. Invocation
mechanics (how each tool asks clarifying questions, how a skill/prompt file is
structured, argument syntax) are tool-specific and live in each wrapper — see
"Why two skills, not one" at the bottom.

## Origin

The pattern is adapted from `architekt-jutra-code/tools/kg-simple-demo/` (a
plugin-based microkernel platform, AJ) — specifically its
`.claude/skills/kg-ontology-designer/references/ARCHITECTURE.md`. That doc is a
stack-agnostic reference; this doc applies it to ECommerceApp's actual shape
(.NET layered monolith, bounded-context folders, homegrown Outbox/Inbox +
sync-query messaging) and adds guardrails discovered while doing that.

## The four-layer pattern

| Layer | Contents | Who fills it | Changes when |
|---|---|---|---|
| 0 — Spine | System, Host | Human, once | Deployment topology changes |
| 1 — Modules | Bounded-context containers | Human lists them; parser populates contents | A module is added |
| 2 — Artifacts | Entities, repositories, actions, endpoints, pages | 100% parser-generated | Every commit |
| 3 — Variability | This system's actual integration/extensibility mechanism | Human designs shape once; parser populates | Rare |
| 4 — Cross-cutting | RBAC, features, governance links | Mostly human/derived | As decisions are made |

Layer 3 is **the one you redesign per project** — don't copy another project's
variability-point node types. AJ's variability point is plugins
(`Plugin`/`Manifest`/`ExtensionPoint`). ECommerceApp has no plugins; its
variability point is the **message broker** — a homegrown Outbox/Inbox (async
pub/sub) plus a synchronous in-process query channel (`ModuleClient`), see
below.

## Relationship vocabulary discipline

Reuse a small set of generic verbs across many node-type pairs instead of one
bespoke name per pair. What's legal between which pair is an explicit allow-list
(`(sourceLabel, type, targetLabel)` triples), validated by the codegen — an
undeclared triple must fail the build, not silently expand the ontology.

ECommerceApp's vocabulary (10 verbs total — 8 reused from the generic starter
set, 2 new, deliberately kept this small):

`CONTAINS` · `PERSISTED_BY` · `OPERATES_ON` · `EXPOSED_BY` · `PUBLISHES` ·
`USES` · `GOVERNED_BY` · `DEPENDS_ON` (reused) — `HANDLED_BY`, `SCHEDULES` (new,
both justified below).

## The design flow

1. **Ask the structural questions** — stack, architecture style, variability
   points, existing docs/knowledge-base to cross-link. Verify claims against
   real code rather than trusting a generic stack cheat sheet (see Guardrail 1).
2. **Ask for target questions in free text** — 5–10 concrete questions the
   graph must answer. Never skip this even under time pressure; a graph
   designed without target questions models the wrong things.
3. **Propose a draft ontology** (layers 0–4 + relationship vocabulary as a
   table) and stop for review.
4. **Dry run** — trace 2–3 *real* cascades through the actual codebase against
   the draft and report the outcome (see Guardrail 2). Amend the draft from
   what the dry run finds.
5. **Tier the MCP tooling** — for each target question, one row of
   `question → Tier-1 tool name → params → intent`, or explicitly Tier 0
   (`read_cypher`) if the question is too open-ended for a fixed template.
6. **Only after confirmation**, write `ontology.json`/`ontology.cypher`, sketch
   the parser list (one per source domain), sketch MCP tool contracts.

## Guardrails (hard rules — established the hard way, keep them)

1. **Verify-before-trust.** A marker/convention claim ("this stack uses
   attribute X for entities") is worthless until grepped/read in the actual
   repo. Generic stack cheat sheets are a starting hypothesis, never a
   citation. Example: ECommerceApp's `Entity` marker is
   `IEntityTypeConfiguration<T>` + `builder.ToTable(...)`, not `[Table]` —
   found by reading `OrderConfiguration.cs`, not by assuming EF conventions.

2. **Dry run before locking the draft, and report both outcomes.** Trace real
   cascades through the codebase against the declared node/edge triples
   *before* writing the ontology file. Report back conversationally either
   way — "ran the simulation, X and Y checked out, Z needs refinement" is
   exactly as valuable a report as "everything fits, ship it." Don't only
   surface problems; a clean pass is real information too, especially in an
   interactive session.
   - Concrete ECommerceApp example: tracing `OrderPlaced` end-to-end
     confirmed 5-module fan-out and caught that `Action -[:EXPOSED_BY]->
     {Endpoint|Page}` needed reversing from an earlier draft, before any
     parser code existed to make that expensive to fix.

3. **Never emit a node for an alias/convenience constant.** If a "role" or
   similar identity string in code is actually a comma-joined alias for
   several real values (e.g. C# `MaintenanceRole = "Administrator, Manager,
   Service"`), the parser must split it and emit edges to the atomic real
   values — never a node for the alias name itself, which doesn't exist as
   an identity anywhere in the actual authorization system.

4. **Don't materialize a derived fact as its own edge if it can drift from
   what it's derived from.** Module-to-module coupling in ECommerceApp is
   answerable by traversing `Module→Action→PUBLISHES→Message→HANDLED_BY→
   MessageHandler→Module` (and the `Query` equivalent) — it is a Tier-1 MCP
   tool (`GetModuleDependencies`), not a stored `Module -[:DEPENDS_ON]->
   Module` edge. A stored duplicate is a second source of truth that can
   silently go stale relative to the edges it summarizes.

5. **Flag convention-dependent parsers explicitly, including their failure
   mode.** A schema-validity check (`validate()` failing the build on an
   undeclared triple) does not catch a parser whose *underlying convention*
   quietly stopped applying — it just returns zero nodes, which looks like
   success. Example: `ScriptModule` extraction assumes RequireJS/AMD
   (`define([...], fn)`); if the frontend ever migrates to ES
   modules/a bundler, the parser won't error, it will silently find nothing.
   The codegen must warn when a previously-nonzero-yield parser returns zero,
   not treat silence as success.

6. **Capability verification, not memory.** Before asserting any tool/library
   capability that will shape the model, verify it against the running
   system or the actual dependency, the same discipline this repo already
   applies to external tools in `pre-edit.instructions.md` §Capability
   verification rule — schema enums, upstream READMEs, or a prior memory
   entry are not proof of current behavior.

7. **Target-questions-first.** Do not draft node/edge types before collecting
   the concrete questions the graph is meant to answer (design flow step 2).

## ECommerceApp ontology — the confirmed model

Living artifact: `tools/kg/seed/ontology.json` (machine-readable, validator
input) + `tools/kg/seed/ontology.cypher` (same schema with full descriptions,
loaded into Neo4j so the ontology itself is queryable).

### Layer 0/1

`System` (ECommerceApp) contains `Host` (two instances: `ApiHost` =
`ECommerceApp.API`, JSON REST; `WebHost` = `ECommerceApp.Web`, server-rendered
MVC/Razor with Areas) **and, separately, `Module`** — Modules are NOT nested
under a specific Host, because both Hosts share the same Application-layer
`Action`s in-process (a Web MVC controller injects an Application service
directly, it does not call the API over HTTP). This is a deliberate departure
from AJ's strict `Host→Frontend/Backend→Module` tree, made because it's what
the real topology is.

Fourteen confirmed Module instances (bounded contexts): `AccountProfile`,
`Backoffice`, `Catalog` (merges `Products`+`Images` — one BC), `IAM`,
`Inventory` (folder: `Availability`), `Checkout` (folder: `Presale/Checkout`),
`Orders`, `Payments`, `Coupons`, `Fulfillment`, `Communication`, `Currencies`,
`TimeManagement`, `Messaging`. `Backoffice` deliberately owns no entities of
its own — it's an intentional admin facade over every other module
(`BackofficeOrderService`, `BackofficePaymentService`, ... each with
`OPERATES_ON` edges into other modules' entities). That's expected fan-out,
not a modeling defect.

### Layer 2 — artifacts

- `Entity`: `IEntityTypeConfiguration<T>` implementation under
  `Infrastructure/<Module>/Configurations/*Configuration.cs`; table name from
  that file's `builder.ToTable(...)` call.
- `Repository`: `I*Repository` interface under `Domain/<Module>/` (verified —
  28 of 30 repository interfaces in the repo live in Domain, not Application;
  the 2 exceptions are `Messaging`'s own `IOutboxRepository`/
  `IInboxCleanupRepository`) + implementation under
  `Infrastructure/<Module>/Repositories`.
- `Action`: public method on an Application-layer `*Service` class.
  query/command classification deliberately **not modeled** — .NET has no
  direct equivalent of a `readOnly`-transaction marker; revisit only if a real
  convention emerges.
- `Endpoint`: `[HttpGet]`/... method on a class under
  `API/Controllers/<Module>/*Controller.cs` that is an API controller —
  verified 2026-08-07 this is **not** simply "has `[ApiController]` on
  itself": 12 of 13 controllers get it transitively by deriving from
  `API/Controllers/BaseController.cs` (which carries `[ApiController]`);
  exactly one (`StorefrontController`) derives from `ControllerBase`
  directly and declares `[ApiController]` itself. A syntax-only parser
  needs both branches — direct attribute, or `BaseController` in the
  (single-level, confirmed no deeper chain exists) base-type list.
- `Page`: MVC action + Razor view under `Web/Areas/<Area>/Controllers` or
  `Web/Controllers`.
- `ScriptModule`: client-side JS loaded via RequireJS/AMD — see Guardrail 5,
  this one is explicitly flagged as convention-dependent in the ontology file
  itself.

### Layer 3 — the variability point (async + sync cross-module integration)

Two channels, deliberately **distinguished by node label, unified by one
shared relation verb** (`HANDLED_BY`) instead of either merging them into one
node type or giving each its own verb:

- `Message` (+ secondary label `ModuleContract`): async, fire-and-forget.
  Marker: record implementing `IMessage`, registered under an explicit string
  key in `MessageTypeRegistry` (deliberately not reflection-scanned).
  Delivered via Outbox/Inbox — 0..N handlers, eventual consistency. `fields`
  property captured directly from the C# record's positional parameters
  (exact, not inferred).
- `MessageHandler`: implements `IMessageHandler<T>` or
  `IIdAwareMessageHandler<T>` (`idAware` property — inbox idempotency guard).
- `Query` (+ secondary label `ModuleContract`): sync, blocking. Marker:
  `IQuery<TResult>`, dispatched via `ModuleClient.SendAsync`. Exactly one
  handler, immediate response — the opposite delivery guarantee from
  `Message`.
- `QueryHandler`: implements `IQueryHandler<TQuery,TResult>`.
- `Job`: implements `IScheduledTask`. Three trigger modes
  (`JobTriggerSource` enum): `Scheduled` (recurring, cron string is **runtime
  DB data**, not statically extractable), `Deferred` (per-entity, one-shot,
  enqueued via `IDeferredJobScheduler.ScheduleAsync` — the caller is a real,
  traceable `Action` or `MessageHandler`), `Manual` (any registered Job is
  always triggerable by an Administrator — a platform-wide capability, not a
  per-job edge worth modeling).

`{Action,MessageHandler} -[:SCHEDULES]-> Job` is the one new verb this
required — justified because a `MessageHandler` scheduling a `Job`
(`OrderPlacedHandler` → `PaymentWindowExpiredJob`) is a real, distinct,
high-value relationship nothing else in the vocabulary captured.

### Layer 4 — RBAC

`Role` (atomic `[Authorize(Roles=...)]` values — `Administrator`, `Manager`,
`Service`) and `Policy` (`[Authorize(Policy=...)]` — e.g. `TrustedApiUser`).
See Guardrail 3 for the alias-splitting rule this required.
`Feature`/event-storming-derived nodes deliberately **not modeled** — that
information lives in event storming docs, not extractable from code beyond
the RBAC signal already captured.

### Notable finding from the dry run

`Domain/Supporting/TimeManagement/Events/JobExecutionCompleted.cs` and
`JobExecutionFailed.cs` are defined but referenced nowhere in the repo — not
raised, not handled, don't even implement `IMessage`. Flagged during the dry
run as a real, unrelated-to-the-graph follow-up (dead code or unfinished
wiring) — the graph would surface this on its own once built (a `Message`
node with zero `PUBLISHES` in-edges and zero `HANDLED_BY` out-edges), no
special node type needed to detect it.

## Target questions + MCP tool tiering (ECommerceApp)

Design-flow step 2's "5-10 concrete questions" for this graph, collected
2026-08-07 from the questions the user actually asks when scoping a new
feature by hand today. Each maps to a Tier-1 tool (typed params, real
ontology triples) or is flagged as explicitly out of scope so Phase 7 does
not silently invent a tool for something this graph structurally cannot
answer (per design-flow step 5 and Guardrail 4 — don't materialize a fact
that can't be honestly derived).

| # | Question (as the user actually asks it) | Tier-1 tool | Traversal |
|---|---|---|---|
| TQ1 | "How does X work / what is it connected to?" | `GetNodeNeighbors(nodeId)` | all in/out edges of one node, generic across labels |
| TQ2 | "What does changing X affect (blast radius)?" | `GetBlastRadius(nodeId, maxDepth)` | forward: `OPERATES_ON`, `PERSISTED_BY`, `PUBLISHES→HANDLED_BY`, `EXPOSED_BY`, `USES`, `SCHEDULES` |
| TQ3 | "What does X need to run / to load Y?" | `GetNodeDependencies(nodeId)` | reverse of TQ2 — for an `Action`: `USES→Query`, `OPERATES_ON→Entity` |
| TQ4 | "What integrations do we have — which BCs talk to which?" | `GetModuleDependencies(moduleId)` | `Module→Action→PUBLISHES→Message→HANDLED_BY→MessageHandler→Module` (+ `Query` equivalent) — already named in Guardrail 4 as the reason `Module-DEPENDS_ON->Module` is *not* a stored edge |
| TQ5 | "Where is the source of truth for BC X?" | `GetModuleOwnership(moduleId)` | `Module -[:CONTAINS]-> {Entity,Repository}` |
| TQ6 | "Does page/endpoint X trigger action Y? Where else is Y called from?" | `GetActionExposure(actionId)` | reverse `EXPOSED_BY` (`Endpoint`/`Page`) + reverse `SCHEDULES` (for a `Job`'s callers) |
| TQ7 | "Who handles message/query X? Any dead contracts (zero handlers or callers)?" | `GetOrphanContracts()` | `Message`/`Query`/`Job` nodes with no `HANDLED_BY`/`PUBLISHES`/`SCHEDULES` edge — generalizes the dry run's `JobExecutionCompleted` finding into a standing tool |
| TQ8 | "Who schedules job X, what's its trigger mode?" | `GetJobSchedulers(jobId)` | reverse `SCHEDULES` + `Job.triggerMode` property |
| TQ9 | "Which actions/pages require role/policy X (RBAC audit)?" | `GetGovernedActions(roleOrPolicyId)` | reverse `GOVERNED_BY` from `Role`/`Policy` |
| TQ10 | "Is there an existing pattern I can reuse for X?" | `FindStructurallySimilarActions(actionId)` | `Action` nodes with overlapping `OPERATES_ON`/`PUBLISHES`/`USES`/`EXPOSED_BY` target-label shape — **heuristic proxy only**, not an authoritative pattern match (see below) |

**Explicitly out of scope — do not build a tool that fakes these:**
- **Effort/time estimates** ("how many changes, how many months"). Not
  derivable from a structural graph. TQ2/TQ3's *node/edge count* is a
  legitimate rough size proxy; no tool should claim to estimate calendar
  time from it.
- **"From scratch or reuse", "which pattern", "which archetype".** These
  are architectural judgment calls a human or LLM makes *using* TQ10's
  structural signal as input — the graph surfaces shape similarity, it
  does not classify patterns itself. Consistent with this doc's opening
  line: a code-derived graph, not an LLM-interpreted one.
- **"What tests exist / are missing for the most sensitive code."** Needs
  a coverage data source this ontology does not have. TQ2 run in reverse
  (who depends on me = high fan-in) is a usable "structurally sensitive"
  proxy today; actual test coverage is a candidate future Layer-4
  addition (a `Test`/coverage import), not Phase 7 scope.
- **"Author of an action" as git authorship.** That's `git blame`/`git
  log`, outside this graph entirely. If the question actually meant
  "which module owns this action," that's TQ1/TQ5.

**Views clarification (confirms existing modeling, no new node type):**
"views" in target-question terms means the `Page` marker (MVC action +
Razor view wiring under `Web/…/Controllers`, already defined in Layer 2
above) and the `ScriptModule` marker (RequireJS/AMD client JS, Layer 3) —
not Razor template internals. TQ6 already covers "does page X trigger
action Y" via the existing `Page -[:EXPOSED_BY]- Action` /
`Page -[:USES]-> ScriptModule` triples; no ontology change needed.

## Implementation plan (kg-codegen)

Phased, one source domain at a time (see Guardrail-adjacent principle:
resist modeling/building everything at once):

0.–1. ✅ **Built** (`tools/kg/kg-codegen/`, C# console app + `KgCodegen.Core`
   library, `net10.0`, syntax-only Roslyn — no `MSBuildWorkspace`). Ports
   `Graph`/`CypherNode`/`CypherEdge`/`GraphMerge`/`Validator`/`Emitter` from
   AJ's TypeScript, plus Roslyn parsers for `Module` (hand-authored
   `SpineCatalog`), `Entity`, `Repository`, `Action`. Validated clean against
   the real repo: 14 `Module`, 33 `Entity`, 28 `Repository`, 201 `Action`
   nodes, 0 ontology errors. Found and fixed one real bug during independent
   validation: `RepositoryParser`'s original `PERSISTED_BY` matching used
   substring `Contains` instead of exact leaf-type-name matching, producing
   false edges wherever entity names share a prefix (`Coupon` vs.
   `CouponUsed` vs. `CouponApplicationRecord` — all real, all in this repo).
   Fixed to unwrap `Task<T>`/`IReadOnlyList<T>`/`T?`/`T[]` and compare exact
   simple names; regression test added.
2. ✅ **Built** (test hardening) — CLI entry point (`Program.cs`) extracted
   into a testable `CliRunner.Run(args, stdout, stderr)`, exercised by
   in-process tests (`--check` write-suppression, timestamped-file write,
   non-zero exit + `error:` on a broken ontology fixture). Added pinned/golden
   facts against the real repo (exact `Module` count, `Coupon` entity's table
   name and FQCN, exact-not-prefix `PERSISTED_BY` edges — the direct
   regression pin for the Phase 0+1 bug — one real `Action` node, lower-bound
   floors for `Entity`/`Repository`/`Action`, zero unknown-label warnings),
   full-pipeline determinism across two runs at real-repo scale, and exactly
   one subprocess test against the actual built executable (catches packaging
   issues no in-process test can see). 19/19 tests pass.
Phases 3 and 4 are split into homogeneous sub-phases rather than kept as the
two original coarse phases — each sub-phase below touches one source
location and one risk profile, matching the granularity Phase 0-2 already
used (decided 2026-08-07, see [[project_ecommerceapp_kg_meta_skill_plan]]).

3a. ✅ **Built** — `Endpoint` (`[HttpGet]`/... on `[ApiController]` under
    `API/Controllers/<Module>/`) + `Page` (MVC action under
    `Web/Areas/<Area>/Controllers` or `Web/Controllers`) — the HTTP-surface
    layer, `Action -[:EXPOSED_BY]-> {Endpoint|Page}`. `SpineCatalog` now also
    emits the two `Host` nodes (`ApiHost`/`WebHost`) the ontology already
    declared. Both parsers share `ControllerParserSupport`; the two
    `[ApiController]` branches (12 controllers inherit it from
    `API/Controllers/BaseController.cs`, `StorefrontController` declares it
    directly) are both covered and both pinned. Real repo: 2 `Host`,
    49 `Endpoint` (= exactly the 49 `[Http*]` attributes in the 14 API
    controllers), 176 `Page`, 227 `EXPOSED_BY`, 0 ontology errors,
    deterministic across runs. **Action-resolution coverage: 48/49 = 98.0 %
    of `Endpoint` and 161/176 = 91.5 % of `Page` nodes carry at least one
    `EXPOSED_BY` edge (209/225 = 92.9 % overall).** The uncovered remainder
    is methods that call no injected service at all (`HomeController.Error`,
    GET form actions returning a bare `View()`) — not failed resolutions:
    zero `Could not resolve action` warnings are emitted. Route extraction
    stays best-effort per plan — 171 MVC pages use conventional routing with
    no explicit `[Route]`, so their `route` is `null` **plus a warning**
    rather than a guess.
    Two honesty guards were added during independent validation:
    `DomainSymbolIndex.ResolveImplementation` (the fallback that resolves
    decorators, e.g. `ICatalogNavigationService` whose only implementation is
    `CachedCatalogNavigationService` — there is no `CatalogNavigationService`
    class, so the `I{Service}`↔`{Service}` convention alone would miss it)
    refuses to answer when more than one class implements the interface, and
    the same refusal covers duplicated simple names; an ambiguous service
    yields a warning, never an edge to an arbitrarily picked class. The index'
    duplicate-name warnings are now surfaced by `CliRunner` instead of being
    collected and dropped. 27/27 tests pass.
3b. Roslyn parser: `Role`/`Policy` (`[Authorize(Roles=...)]` /
    `[Authorize(Policy=...)]` on the controllers found in 3a — `{Endpoint|
    Page} -[:GOVERNED_BY]-> {Role|Policy}`), with the alias-splitting rule
    from Guardrail 3 (a comma-joined role constant must resolve to atomic
    `Role` nodes, never a node for the alias string itself). Kept separate
    from 3a because the guardrail adds real parsing risk (splitting logic)
    that a plain attribute-presence parser doesn't have.
4a. Roslyn parser: `Message`/`MessageHandler` (async Outbox/Inbox side of
    the variability point — `IMessage`/`MessageTypeRegistry`,
    `IMessageHandler<T>`/`IIdAwareMessageHandler<T>`).
4b. Roslyn parser: `Query`/`QueryHandler` (sync `ModuleClient` side —
    `IQuery<TResult>`, `IQueryHandler<TQuery,TResult>`). Split from 4a
    because the two channels have opposite delivery guarantees (0..N
    eventual-consistency handlers vs. exactly-one immediate response) and
    are extracted from different marker interfaces.
4c. Roslyn parser: `Job` (+ the new `SCHEDULES` verb from
    `{Action,MessageHandler} -[:SCHEDULES]-> Job`) — depends on 4a/4b
    existing first since `SCHEDULES` sources from `Action`/`MessageHandler`
    nodes. Three trigger modes per `JobTriggerSource`; `Scheduled`'s cron
    string is runtime DB data, not statically extractable (stays a gap
    until Phase 6's `overrides.yaml`).
5. JS/AMD parser: `ScriptModule` — lowest confidence, built last, carries the
   staleness-warning requirement from Guardrail 5.
6. `compose.yml` (Neo4j) + `overrides.yaml` for facts no parser can infer
   (e.g. the real cron string for `Scheduled` jobs), replacing the Phase 0+1
   stand-in `SpineCatalog.cs`. Includes the load step (seed `.cypher` →
   running Neo4j) that nothing describes today — see "Querying the graph
   today" below.
7. MCP server — Tier-1 query tools per the target-questions tiering below,
   wrapping the Neo4j instance stood up in Phase 6. **Stdio transport
   only** — no HTTP-streamable variant, unlike this repo's RAG MCP servers
   (see "Querying the graph today" below for why that asymmetry is
   intentional).

## Querying the graph today

As of Phase 2, kg-codegen only emits a static `tools/kg/kg-seed.*.cypher`
file — there is **no live Neo4j instance and no MCP server** for this
project's own graph yet. Confirmed by inspection: `docker-compose.yaml` has
no `neo4j` service (only `api`, `web`, `rag-tools`, `qdrant`), and
`.vscode/mcp.json` has no Neo4j entry (only the RAG vector-search servers and
the `context-mode` sandbox). This is different from the AJ platform's
`neo4j-aj-kb` MCP server referenced by the `aj-kg-query` skill — that graph
and server already exist for AJ; ECommerceApp's equivalent is Phase 6
(stand up Neo4j, load the seed) + Phase 7 (MCP tool layer) above, neither
started. Until then, inspecting the graph means loading
`kg-seed.*.cypher` into a Neo4j instance by hand (e.g. `cypher-shell`) and
querying it directly.

## Why two skills, not one

GitHub Copilot and Claude Code interpret a "skill" through different
mechanics — invocation syntax, how each host asks the human a clarifying
question (`vscode_askQuestions` in VS Code Copilot vs. Claude Code's
`AskUserQuestion` tool vs. a plain numbered-list chat reply as the
lowest-common-denominator fallback — see `pre-edit.instructions.md`
§Clarification policy for the pattern this repo already uses), frontmatter
shape, and how deep a workflow it can safely encode. Forcing one file to
serve both either weakens it to the lowest common denominator or breaks in
whichever tool it wasn't written for. Only the content above — the
methodology, the layer model, the guardrails, the confirmed ECommerceApp
model — is genuinely shared; it lives here exactly once. Everything
tool-specific (frontmatter fields, checkpoint phrasing, argument syntax)
lives in the two thin wrapper skills, not here.
