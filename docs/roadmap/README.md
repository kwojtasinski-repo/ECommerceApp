## Future architectural considerations

> Items for future discussion and implementation. Not blocked — deferred by choice until
> we have enough production experience and confidence in the current design.

| #      | Topic                                                   | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | When to act                                                                                                                                                     | Tracking                                                                    |
| ------ | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **F1** | **ADR slimming — split implementation details**         | ADRs are growing large (many exceed 300 lines). Split detailed implementation sections (domain model specs, handler contracts, EF configurations, validation rules) into dedicated `docs/adr/implementation/XXXX-impl.md` files linked from the parent ADR. The ADR retains high-level design decisions; the implementation file captures how the solution works in detail with fine-grained requirements.                                                                                                                                                                                                                                                                                           | When any ADR exceeds ~250 lines, or during the next atomic-switch phase when ADRs are reviewed                                                                  | `docs/adr/implementation/` directory (to be created)                        |
| **F2** | **Common location for public event contracts**          | Currently each BC defines its own message records under `Application/<BC>/Messages/`. Consider a shared `Application/Messaging/Contracts/` or per-publisher namespace convention so consumers can discover available events without scanning every BC. Trade-off: shared location vs. BC autonomy.                                                                                                                                                                                                                                                                                                                                                                                                   | Future design discussion — after all BCs are implemented and cross-BC message count stabilises                                                                  | —                                                                           |
| **F3** | **Saga / Orchestrator pattern evaluation**              | Some multi-step flows (e.g., PlaceOrder → Payment → Inventory → Fulfillment) are currently choreography-based (event chains). Two structural gaps identified: (1) no compensation on partial failure — if Inventory.ReserveStock fails after Payments.CreatePayment succeeds, there is no rollback signal; (2) no saga state persistence — failed event chains leave no structured breadcrumb. **Option A** (recommended first): add `OrderPlacementFailed` compensation handlers on top of the existing `IMessageBroker` infrastructure. **Option B** (future): originally scoped as an `OrderLifecycleSaga` process manager entity; **superseded (2026-07-26)** by a generic saga/orchestration engine once Refund, cart-corruption recovery, and Inventory→Checkout lock propagation surfaced as further concrete saga candidates beyond Order Placement — see [`generic-saga-orchestration-proposal.md`](./generic-saga-orchestration-proposal.md). Requires Outbox pattern first either way. Do not refactor prematurely. **Update:** Option A is implemented (ADR-0026); Outbox (all 5 phases: schema, poller/dispatcher, retrofit, Inbox idempotency, cleanup jobs) is fully done and validated (2026-08-02) — remaining gap is only the generic saga engine itself — see [`order-placement-compensation-followup.md`](./order-placement-compensation-followup.md) and [`generic-saga-orchestration-proposal.md`](./generic-saga-orchestration-proposal.md). | When we confirm a real compensation gap in production, OR when Option A is agreed to be insufficient                                                            | [`saga-pattern.md`](./saga-pattern.md) — full analysis, gap map, sequencing; [`order-placement-compensation-followup.md`](./order-placement-compensation-followup.md) — active follow-up plan; [`generic-saga-orchestration-proposal.md`](./generic-saga-orchestration-proposal.md) — proposed generic engine, requirements + implementation plan |
| **F4** | **Event handler chain refactoring** ⚠️ _crucial_        | Several handlers publish new events from within an event handler (e.g., `OrderPaymentExpiredHandler` handles `PaymentExpired` → cancels order → publishes `OrderCancelled`). While this works for the current in-memory broker, it creates implicit chains that are hard to trace, test in isolation, and reason about failure/retry semantics. Refactor selected flows to use direct method calls within a single BC or introduce an explicit orchestrator where the chain crosses BC boundaries. **Update:** the flagged `PaymentExpired`→`OrderCancelled` chain was already flattened in an ADR-0026 amendment — `OrderPaymentExpiredHandler` no longer publishes `OrderCancelled`. That event is **not unused**, though: `OrderService.CancelOrderAsync` publishes it directly from the manual-cancel path (`OrdersController.Cancel`), and it still has 4 live handlers (Inventory, Coupons, 2× Communication) — it's just no longer reached via the auto-expiry chain. Remaining publish-from-handler cases (`ShipmentDelivered/Failed/PartiallyDelivered` in Inventory) are low-risk leaf publishers, not chains, and are still fully duplicated (no shared base/helper yet) — dedup planned as future-proofing, see [`order-placement-compensation-followup.md`](./order-placement-compensation-followup.md) workstream 3. | After the current design is validated in production and we have clarity on which chains are problematic. Priority: high — affects debuggability and resilience. | [`order-placement-compensation-followup.md`](./order-placement-compensation-followup.md) |
| **F5** | **ModuleClient evolution — universal cross-BC adapter** | `ModuleClient.PublishAsync` already uses `GetServices()` + `foreach` — KI-007 ✅ fixed. **Phase 2 ✅ complete (2026-05-10)**: `IModuleClient.SendAsync<TResult>(IQuery<TResult>)` live; `IOrderExistenceChecker` deleted; `Application/Sales/Shared/` folder removed; 3 query handlers wired (`OrderExistsQuery`, `StockAvailableQuery`, `CompletedOrderCountQuery`); `CouponService`, `RefundService`, `ShipmentService`, `StockAvailabilityCheckerAdapter`, `CompletedOrderCounterAdapter` all migrated to `IModuleClient`.                                                                                                                                                                        | Phase 2 complete — Phase 3 (migrate remaining per-BC adapter classes) if needed                                                                                 | —                                                                           |
